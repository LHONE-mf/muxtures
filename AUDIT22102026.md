## 4. Детальный разбор этапа 1f (uncommitted, staged)

### Реализовано (код прочитан, работает на уровне слоёв domain/data/calc)
- **Роли** (`domain/Roles.kt`): ADMIN, TECHNOLOG, OPERATOR, QC, OBSERVER + 9 гранулярных
  Capability; матрица прав в `RolePermissions`; тексты отказов для UI и аудита.
- **PIN** (`calc/PinHash.kt`): PBKDF2-HMAC-SHA256, 120k итераций, соль 16 байт SecureRandom,
  constant-time сравнение `MessageDigest.isEqual`; валидация формата (4–8 цифр, ≥6 для админа).
- **AuthRepository**: создание пользователей (первый обязан быть ADMIN), login/logout,
  смена PIN (со старым), сброс PIN админом, деактивация (не удаление) профиля,
  защита от деактивации единственного администратора.
- **Брутфорс-защита**: 5 неверных PIN → логин блокируется на 60 с, события LOGIN_FAIL/LOGIN_LOCKED пишутся в аудит.
- **Журнал аудита**: таблица `audit_log` (append-only: в DAO нет UPDATE/DELETE намеренно),
  фасад `Audit.record` + индекс по ts; событие APP_START при запуске.
- **Guard**: единая точка проверки права; каждый отказ пишется в аудит как DENIED.
- **Запрет удаления журнала**: `JournalRow.immutable=true` проставляется всегда;
  `JournalRepository.remove()` физически ничего не удаляет, возвращает false и пишет DELETE_BLOCKED;
  обновления разрешены и логируются диффом старого→нового (verdict/массы/вязкость/плотность/комментарий).
- **ViewModel**: `can(cap)` через DataHolder.guard; CREATE_BATCH блокирует сохранение без права;
  SIGN_OFF требуется при изменении вердикта, иначе EDIT_ACTUALS.

### НЕ реализовано (что мешает назвать 1f выполненным)
1. **UI авторизации отсутствует.** В MainActivity нет ни одного упоминания PIN/login/экрана входа
   (grep пустой). Приложение стартует как «гость»: currentUser=null → все Capability запрещены,
   но пользователя никто не просит представиться. Нужны: экран логина, первый запуск = создание админа,
   экран управления пользователями, просмотр audit_log (VIEW_AUDIT), кнопка logout.
2. **Нет юнит-тестов на 1f.** Ни одного теста на RolePermissions, PinHash (round-trip/формат/блокировки),
   Guard. Тесты есть только на расчёты.
3. **Миграция схемы users**: версия БД поднята до 3, в MIGRATION_2_3 создаётся таблица users —
   нужно проверить корректность SQL и тест на устройстве (Room schema выгрузка есть).
4. **Сборка не проверена** после добавления файлов 1f; версия не bumped (осталась 1.5.0/10).
5. Мелкие замечания по коду:
   - `Audit.record` глотает исключения (пишет в logcat) — осознанный компромисс, но потерю
     события аудита стоит подсветить в UI;
   - `AuthRepository` синхронный (allowMainThreadQueries) — приемлемо для малых выборок, риск при росте users;
   - имя пользователя для аудита хранится дубликатом строкой (name+role) — исторично правильно, но при переименовании старые записи не обновятся (это feature, не bug).

## 5. Прочие несоответствия, выявленные аудитом

- **Этап 1c систематически засчитывался как выполненный при отсутствии кода** — единственный
  полностью проваленный пункт плана. Требуется отдельный коммит: NavHost + разнесение MainActivity
  на экраны (Calc/Materials/Journal/Tasks/Settings/Login) без изменения поведения.
- Релизы: v1.4.0/v1.4.1 публиковались битыми (crash-on-startup), v1.4.2 исправил потерю @Database,
  v1.4.1 ранее — main-thread init БД. Итог: v1.5.0 стабилен (подтверждено пользователем).
- В истории git есть коммиты «Stage 0/1a…» без сборки — контроль «собери перед отчётом» должен
  стать обязательным шлагбаумом (см. рекомендации).

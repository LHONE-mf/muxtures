# 00_RULES — правила для Qwen (загружай в КАЖДУЮ сессию вместе с файлом этапа)

## 1. Проект
Android-приложение **SlurryCalc Lab**: журнал замесов электродной пасты (катод/анод Li-ion): рецептуры, задания, точные массы, отклонения, вязкость, степень перетира, параметры мешалок, достаточность времени перемешивания.
Kotlin, Jetpack Compose (Material 3), Room, работает офлайн, интерфейс на русском. `applicationId` и пакет: `com.slurrycalc.lab`. minSdk 26, target/compile 34.
Новый applicationId выбран нарочно: приложение ставится рядом со старым и не трогает его данные.

## 2. Как ты работаешь
1. В сессии выполняй ТОЛЬКО указанный этап. Если считаешь, что нужен другой этап, остановись и задай вопрос (шаблон в разделе 7).
2. Начни с чтения `docs/STATUS.md` и файла этапа. Проверь предусловия командами, которые перечислены в этапе. Если предусловие не выполнено, остановись и сообщи.
3. Работай в ветке `stage/SXX` (XX = номер этапа) от актуальной `main`. Делай маленькие коммиты. В `main` сливай (`git merge --ff-only`) только когда пользователь напишет «слить».
4. Теги, релизы, публикация: только по явной команде пользователя.
5. Коммит допускается только при зелёной сборке и зелёных тестах. Незавершённое сохраняй в ветке `wip/<имя>` с пометкой «WIP, не собирается».
6. **Запрещены массовые автоматические правки** (скрипты, режущие код по скобкам/регуляркам, sed по многим файлам). Меняй файлы по одному, после каждого логического шага собирай проект.
7. **Не меняй тесты, чтобы они прошли.** Если тест из этапа не сходится, найди причину в коде. Если уверен, что ошибка в числах этапа, остановись и покажи расчёт вручную.
8. Бюджет: когда израсходовано около 70 % лимита вызовов, не начинай новых правок. Доведи текущее до компилируемого состояния, закоммить, обнови `docs/STATUS.md` и сделай отчёт.
9. Не выдумывай формулы, допуски и справочные значения. Всё, что не дано в этапе, берётся из настроек/БД и помечается «ПРИМЕРНОЕ, уточнить».
10. Не добавляй библиотеки сверх списка раздела 4. Если нужна другая, остановись и спроси. Если сети нет (`--offline`) и зависимости нет в кэше Gradle, остановись и спроси.
11. Перед `git checkout`, `git stash`, `git reset` проверь `git status`; несохранённой нужной работы быть не должно.
12. Если в файле этапа есть противоречие или неясность: НЕ угадывай, задай вопрос.

## 3. Что значит «готово»
Этап готов только если выполнено всё:
1. `./scripts/check_stage.sh SXX` печатает последней строкой `STAGE SXX: PASS`.
2. Все пункты чек-листа этапа подтверждены доказательствами (файл:строка, имя теста, вывод команды).
3. Работа закоммичена и запушена в `stage/SXX`; `git cat-file -t <хэш>` вернул `commit`.
4. `docs/STATUS.md` обновлён.
Слово «готово» без этого запрещено. Не знаешь или не смог проверить: так и напиши («НЕ ПРОВЕРЕНО, причина …»).

## 4. Технические соглашения
**Версии:** строго как в `docs/salvage/versions.md` (подтверждены работающей сборкой). Не обновляй версии.
**Разрешённые библиотеки:** androidx core-ktx, activity-compose, lifecycle (runtime-compose, viewmodel-compose), Compose BOM (ui, material3, ui-tooling-preview, material-icons-core), navigation-compose, Room (runtime, ktx, ksp-compiler), kotlinx-coroutines-android, ZXing core (только генерация QR). Тесты: junit4, kotlinx-coroutines-test, robolectric, androidx.test:core, room-testing. Графики рисуются на Compose Canvas, PDF через `android.graphics.pdf.PdfDocument`.
**Пакеты:** `com.slurrycalc.lab.{calc, security, data, domain, ui, util}`. `calc`, `security`, `util` не зависят от Android (чистый Kotlin, тесты на JVM). Тесты БД идут через Robolectric (in-memory Room).
**Единицы:** суффикс имени = единица: `_mg` (Long), `_g`, `_kg`, `_mm`, `_m`, `_rpm`, `_pas` (Па·с), `_mpas` (мПа·с, только UI/импорт), `_kgm3`, `_ml`, `_c`, `_s`, `_min`, `_ms` (время Unix в мс), `_pct`. В БД и в `calc`: массы `Long` в мг, вязкость Па·с, плотность кг/м³, диаметры в мм (в `calc` физика переводит в метры внутри). Перевод в удобные единицы только на границе UI. `Double`/`Float` для масс запрещены.
**ID:** первичные ключи UUID-строки (кроме журнала аудита: числовой `seq`). Время: Unix мс через интерфейс `Clock` (в тестах подменяется).
**Стандартные поля** каждой справочной/рабочей сущности: `id`, `createdAtMs`, `updatedAtMs`, `deletedAtMs` (мягкое удаление, физически не удаляем).
**Журналы (append-only):** взвешивания, стадии, измерения, движения материалов, аудит не редактируются: исправление = новая запись со ссылкой `supersedesId` и обязательной причиной.
**Аудит:** каждое изменение данных, вход/выход, отказ доступа пишет запись в аудит (хэш-цепочка).
**Права:** проверка в слое репозиториев/сервисов через `AccessGuard`, не только скрытием кнопок.
**Ошибки расчётов:** `CalcResult.Ok/Err`, без исключений для ошибок ввода пользователя. `!!` запрещён.
**Строки UI:** в `res/values/strings.xml`. Числа вводятся и с запятой, и с точкой.
**Схема Room:** до этапа S27 при изменении схемы повышай `version` на 1 (в debug допускается `fallbackToDestructiveMigration`). Данные в приложении до S27 считаются тестовыми. С S27 только миграции.

## 5. Стандартные команды
- Сборка и тесты: `./scripts/check_stage.sh SXX` (сам вызывает gradle; без сети `GRADLE_FLAGS=--offline` по умолчанию).
- Только тесты: `./gradlew --offline testDebugUnitTest`, один класс: `--tests '*ИмяТеста*'`.
- Списки проверки этапа: `docs/stages/SXX.files` (обязательные файлы) и `docs/stages/SXX.tests` (класс, минимум тестов). Создай их в начале этапа ТОЧНО по перечню из файла этапа. Пути в этапах записаны сокращённо: `M=app/src/main/java/com/slurrycalc/lab`, `T=app/src/test/java/com/slurrycalc/lab`; в списках пиши полные пути. Не удаляй и не ослабляй строки списков.

## 6. Шаблон отчёта (в конце сессии)
```
ОТЧЁТ SXX
Ветка и коммит: stage/SXX  <хэш>   (git cat-file -t → commit)
Вывод ./scripts/check_stage.sh SXX (СЫРОЙ, без правок, последние 50 строк):
<вставь>
Чек-лист этапа: каждый пункт «✔ <доказательство>» или «✘ <причина>»
Отличия от этапа и их причины:
Не сделано / сомнения:
Вопросы к пользователю (по шаблону раздела 7):
Что делать дальше:
```
Все числа (число тестов и т. п.) бери только из вывода скриптов. Все упомянутые хэши проверь `git cat-file -t`.

## 7. Шаблон запроса к пользователю
Пользователь не программист. Не пиши «пришли данные» или «уточни параметры». Формат строго такой, не больше 3 запросов за раз:
```
ЗАПРОС №N: <название>
Что нужно:       точное название данных или файла
Зачем:           какая функция от этого зависит
Где взять:       где это найти (паспорт прибора, этикетка, лабораторный журнал, меню прибора)
Формат:          CSV / фото / текст; разделитель, единицы
Образец:         2–3 строки с реальной структурой
Как передать:    положить файл в docs/input/<имя> или вставить текстом в чат
Если нет данных: что сделаю по умолчанию (будет помечено «ПРИМЕРНОЕ»)
Блокирует ли:    да / нет
```
Решения оформляй вариантами A / B / C, один отмечен «рекомендую» с причиной в одну строку. Технические термины поясняй в скобках. Не спрашивай то, что можно узнать из кода.
